# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with
code in this repository.

This is a personal GNU Emacs configuration (`~/.emacs.d`), maintained since
2008. It is a configuration repo, not an application — there is no test suite.
"Running" it means loading the Emacs Lisp into a running Emacs.

## Layout & load model

`init.el` is the entry point. It runs `(server-start)`, extends `load-path`
with the source directories, then `require`s each config module **in a
deliberate, dependency-ordered sequence**. Order matters:

1. `basic-*` modules first — these have **no third-party dependencies**.
2. `package-conf` (sets up `package.el`/`package-vc` and claims the packages
   that must precede everything else), then dependent modules.
3. `custom/custom.el` is loaded as `custom-file` (auto-generated by Emacs
   Custom — do not hand-edit; it holds `custom-set-variables` /
   `custom-set-faces`).
4. `custom/langs/*` language modules last.

Source directories (all added to `load-path`):

- `custom/` — personal configuration modules, one concern per file
  (`*-conf.el`).
- `custom/langs/` — per-language setup (`java-conf.el`, `clojure-conf.el`,
  `go-conf.el`, …).
- `artifacts/` — vendored third-party `.el` files that are unavailable/misplaced
  in ELPA or carry small local patches. Kept in-repo intentionally.
- `solutions/` — reusable standalone Elisp libraries (e.g. `functions.el` = misc
  helpers).
- `foreign/` — a Go-based Emacs dynamic module (see below).
- `custom/mysnippets/` — YASnippet snippets, organized by major mode.

## Package management

**The built-in `package.el` is the package manager, and every package is
fetched from git via `package-vc`** — set up in `custom/package-conf.el`.

**`package-archives` is empty, and must stay empty.** The ELPA hosts
(`elpa.gnu.org`, `elpa.nongnu.org`, `melpa.org`) are not reachable from the
network this configuration runs on — that is the reason it used straight.el,
and the reason it uses `package-vc` now. Starting Emacs on a fresh clone must
complete without a single connection to them, so every package, including the
ones that live on GNU ELPA, comes from a git repository: the GNU ELPA ones
from their `github.com/emacs-straight/*` mirrors. `package-conf` additionally
unbinds the archives for the duration of every installation, so that filling
the list in for one manual install cannot put an archive back underneath a
`:vc` checkout.

Packages are declared with `use-package` plus a `:vc` recipe naming the
upstream repository and branch:

```elisp
(use-package cider
  :vc (:url "https://github.com/clojure-emacs/cider.git"
       :branch "master"))
```

Notes on `:vc`:

- `use-package-vc-prefer-newest` is set to `t` in `package-conf`. Without it
  `:vc` checks out the latest *release tag* rather than the tip of the branch.
- `:vc` installs only when the package is not installed yet, and a package
  **bundled with Emacs counts as installed** — `org`, `eglot`, `flymake`,
  `xref`, `project`, `jsonrpc`, `external-completion` and `eldoc` are
  therefore claimed with the `k/package-vc-install` helper instead, which
  tests `package-alist` and so shadows the built-in copy. Each is there
  because current `eglot` (or org) asks for a version newer than Emacs 30.2
  bundles; `seq`, `map` and `let-alist` need no entry, being bundled new
  enough.
- `k/package-vc-install` is also the way in when the URL has to be computed
  (`organic-green-theme` and `ejc-sql` pick ssh or https by `system-type`);
  `:vc` takes a literal spec and cannot.
- There is no `:files` equivalent. Use `:lisp-dir` when the elisp is not at
  the repository root (`clomacs`, `treemacs`), and `:main-file` when the file
  is not named after the package (`lv`). Where two packages share one
  repository (`magit`/`magit-section`, `vertico`/`vertico-directory`), each
  gets its own checkout.
- Dependencies that no `use-package` declaration names are listed, in
  dependency order, in `package-conf`. With no archives there is no fallback:
  a requirement missing from that list is simply not installed, and the
  package that needed it is quietly broken — `package-conf` warns by name when
  this happens (`unclaimed dependencies`). Order matters, since a package
  reached before the one it needs cannot find it.
- Installation runs inside `k/package-vc-isolated`, which unbinds the archives,
  signature checking (nothing git-cloned is signed, and the check otherwise
  imports a keyring and spawns gpg once per package) and the editing mode
  hooks. The last one is not optional: generating autoloads visits the
  package's files in `emacs-lisp-mode`, which runs `my-lisp-coding-hook` from
  `appearance`, and until paredit, rainbow-delimiters and idle-highlight-mode
  are on disk that hook signals — which used to fail the installation of every
  package after the first one that did not install.
- `use-package-always-ensure` must stay nil — its default predicate excludes
  only `:load-path`, so it would add `:ensure t` to `:vc` declarations and
  package.el would race package-vc for the same name.
- `package-conf` carries several `define-advice` corrections to `package-vc`
  itself; each one documents in its docstring what breaks without it. They are
  not stylistic — a configuration this size does not install without them.

A legacy ELPA path also exists (`custom/elpa-conf.el` defines the `use-elpa`
helper), used only by the two commented-out modules `lua-conf` and `irc-conf`.
The `package-selected-packages` list inside `custom.el` is a legacy artifact,
not the source of truth.

Checkouts live in `elpa/<pkg>-<version>/` and are ordinary git working trees:
edit in place, then `M-x package-vc-rebuild`; `M-x package-vc-upgrade` pulls.
`package-vc-register-as-project` puts them all into `C-x p p`.

## Conventions

- **Every module file ends with `(provide 'feature-name)`** and is wired into
  `init.el`'s require list. Adding a new module = create the file with a
  matching `(provide ...)`, then add a `(require ...)` to `init.el` in the
  correct position.
- **Personal interactive commands are namespaced with a `k/` prefix** (e.g.
  `k/clojure-eval-last-sexp`). Follow this when adding user-facing commands.
- Some config modules define a `*-highlight-initialize` function that adds
  `font-lock` keywords so custom macros (like `k/package-vc-install`) are
  highlighted in `emacs-lisp-mode`.

## `.gitignore` — whitelist model

`.gitignore` **ignores everything (`*`) by default**, then re-includes only
specific extensions (`*.el`, `*.org`, `*.md`, `*.go`, `*.yasnippet`) inside
explicitly whitelisted directories. A new file is tracked **only** if both its
extension and its directory are whitelisted — adding a file in a new directory
requires a new `!dir` entry. `communications.el`, `ejc-databases.el`, and
`.mc-lists.el` are explicitly ignored (local/secret data).

## Applying changes

There is no build step for the Elisp itself. To apply a change to a running
Emacs, eval the buffer/defun (`C-M-x`, `C-x C-e`) or `M-x load-file`; a full
restart re-runs `init.el`.

**Do not byte-compile a module to check it.** `use-package` installs a `:vc`
package at *compile* time, so `emacs -batch -f batch-byte-compile
custom/<module>.el` clones packages into `elpa/` as a side effect — and in
`--batch` `package-activate-all` never runs (it is conditional on
`user-init-file`), so the already-installed ones are not on `load-path` and
the compile fails in confusing ways. To check a module reads cleanly:

```sh
emacs --batch --eval '(with-temp-buffer (insert-file-contents "custom/<module>.el") \
  (goto-char (point-min)) (condition-case e (while t (read (current-buffer))) \
  (end-of-file (message "OK")) (error (message "%S" e))))'
```

To test the whole configuration without touching the live one, copy it into a
throwaway `HOME` and let it install from scratch:

```sh
emacs --batch --eval "(defalias 'server-start #'ignore)" \
      --eval "(progn (require 'package) (package-activate-all))" \
      -l <copy>/.emacs.d/init.el
```

## `foreign/` — Go dynamic module

`foreign/` builds a C-shared Emacs module (`foreign-fmt.so`) from Go for fast
text manipulation (JSON/XML/EDN pretty-printing, in-file find/replace). Build
with `make` (or `make all`) inside `foreign/`; `foreign.el` auto-builds it on
load via `foreign-ensure-so`. It is currently **disabled** in `init.el` (the
`(require 'foreign)` line is commented out).

## Tooling notes

- **Tree-sitter** grammars and `*-ts-mode` mappings are configured in
  `custom/tree-sitter-conf.el`; install grammars via
  `M-x treesit-install-language-grammar`.
- **LLM integration** (`custom/llm-conf.el`) uses `gptel` pointed at a **local
  llama.cpp server** (OpenAI-compatible API on `localhost:8080`); the file
  header documents the `llama-server` invocation.
